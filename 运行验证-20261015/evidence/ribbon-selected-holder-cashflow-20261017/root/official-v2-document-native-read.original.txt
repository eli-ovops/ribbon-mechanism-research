L192: # Theta vaults architecture
L193: ## Vault flow example
L194:   1. User deposits 100 ETH into T-ETH-C (ETH call).
L195:   2. On Friday 8 am UTC, the vault closes the previous week round and subsequently uses 100% of its funds to mint 100 cite72†otokens†opyn.gitbook.io , which are ERC20 representations of options contracts. The 100 ETH is locked for a week in Opyn.
L196:   3. After receiving the 100 otokens, the vault puts it up for auction on cite73†Paradigm .
L197:      * Registered users can participate and bid on the otokens. They pay the premiums for the otoken in ETH. Paradigm can use different kinds of auctions to maximise depositors' returns (e.g. cite74†blind auctions†en.wikipedia.org )
L198:      * At the end of the auction, the vault collects 1 ETH in premiums in the form of ETH.
L199:      * Any remaining otokens that are not bought are burned, redeeming 1 otoken for 1 unit of collateral from Opyn.
L200:   4. On the next Friday 8 am UTC,
L201:      * If the options expire in the money, the vault withdraws less than 100 ETH from Opyn.
L202:      * If the options expire out the money, the vault withdraws exactly 100 ETH.
L203:   5. Let's say it expires out the money. The vault repeats step 2 with 101 ETH (original 100 ETH + 1 ETH premium).

L205: Name  | Description
L206: --- | ---
L207: cite75†libraries/Vault.sol | Contains all data structures shared across all vault types
L208: cite76†libraries/VaultLifecycle.sol | Contains all logic related to how the Vault functions on a weekly basis
L209: cite77†vaults/BaseVaults/base/RibbonVault.sol | Contains all common logic like accounting and options rolling shared across RibbonThetaVault and RibbonDeltaVault.

L211: ## Deposit Flow
L212: 
L213: IMPORTANT: this is a technical explanation, if you need assistance on making a deposit please refer to cite79†this page !
L214: 
L215:   1. The user deposits 1 ETH into TV.
L216:   2. We first check if they have an existing `DepositReceipt` from the past `round`. Using the `round` and `amount`, we update the `unredeemedShares` field. This essentially tracks how many shares the user owns, but has not yet redeemed.
L217: 
L218:     `struct DepositReceipt {
L219:     	round
L220:     	amount
L221:     	unredeemedShares
L222:     }
L223:     `
L224:   1. We create the DepositReceipt with the new details.
L225:   2. At `rollToNextOption`, the vault will mint all the shares that are owed to users to `address(this)`. This increments the `vaultState.round`.
L226:   3. Since the round is concluded, the user's vault shares should show up by calling `RibbonVault.shares(account)`
L227: 
L228: The end result:
L229:   * Their shares show up automatically once the round concludes.
L230:   * `DepositReceipt`s are used to track all the user's unredeemed shares. This is used for withdrawals and redemptions in the future.
L231: ## Withdrawal Flow
L232: 
L233: IMPORTANT: this is a technical explanation, if you need assistance on making a withdrawal please refer to cite80†this page !
L234: 
L235: The withdrawal flow is slightly more involved. We have two types of withdrawals - Standard and Instant withdrawals.
L236: ### Standard withdrawals
L237:   * Withdrawals are created with the `initiateWithdraw` function, which queues the shares to be burned.
L238:   * Withdrawals are completed with `completeWithdraw` function, which burns the shares, and returns the assets.
L239:   * Users can only call `completeWithdraw` only AFTER the week's Friday 10am UTC. For example, the user calls `initiateWithdraw` on Wednesday. They can only complete the withdrawal after the same week's Friday 10am UTC.
L240:   * Withdrawals stack on top of each other. This means that if I do `initiateWithdraw(10)`, and I do `initiateWithdraw(20)` again, I will have a total withdrawal of 30 shares by Friday.
L241: ### Instant withdrawals
L242: 
L243:   * Instant withdrawals are only accessible to funds that are deposited mid-week.
L244:   * For example, user deposits 10 ETH into TV on Wednesday. They can call `withdrawInstantly` to return up to 10 ETH, from Wednesday till Friday.
L245: ## Share Redemption Flow
L246: 
L247: IMPORTANT: this is a technical explanation, if you need assistance on redeeming your vault shares please refer to cite81†this page !
L248: 
L249: As mentioned before, when the user deposits into the vault, the vault mints and holds custody of the user's shares on `address(this)`. This is not ideal for protocols or Meta-Vaults that want to hold custody of their shares. By calling the `redeem` or `maxRedeem` function, contracts are able to take custody of their vault shares.
L250: The share redemption flow is also triggered implicitly when users call `initiateWithdraw`.
